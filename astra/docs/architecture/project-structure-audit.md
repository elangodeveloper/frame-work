# JARVIS Framework: Project Structure Audit & Migration Plan

**Date**: October 2026  
**Status**: Comprehensive File Structure & Architecture Audit  
**Author**: Principal Software Architect, Rust Compiler Engineer & Framework Specialist

---

## 1. Executive Summary & Purpose

The goal of this audit is to evaluate the existing file organization of the **JARVIS** repository, distinguish the internal framework implementation from applications generated by the framework, identify structural weaknesses, and establish a standardized, production-ready project architecture.

JARVIS combines:
1. **Object-Oriented Analysis & Design (OOAD)** with SOLID principles and class-based components.
2. An **Ahead-of-Time (AOT) Rust Template Compiler** (`compiler/jarvis-compiler`).
3. **Fine-Grained Reactive Primitives** (`signal`, `computed`, `effect`, `resource`) with **Zero Virtual DOM** and **Zero RxJS**.
4. **Hierarchical Dependency Injection** (`inject()`, `Injector`, `InjectionToken`).
5. **Decoupled Styling & Adapters** (`@jarvis/styles`, PrimeNG adapter, Tailwind integration).
6. **Angular-Inspired Feature-Based Organization** for enterprise applications.

## 3. Detailed Subsystem Analysis

### 3.1 Rust Compiler (`compiler/jarvis-compiler`)
- **Location**: `compiler/jarvis-compiler/`
- **Modules**: `src/lexer.rs`, `src/parser.rs`, `src/ast.rs`, `src/ir.rs`, `src/codegen.rs`, `src/diagnostics.rs`, `src/expr.rs`.
- **Status**: Passes 13 automated Rust unit tests (`cargo test`). Compiles templates into fine-grained JavaScript view factories that invoke `Renderer` methods directly.
- **Evaluation**: The Rust crate is cleanly decoupled from Node.js runtime code. It operates via standard I/O and JSON IPC, making it compatible with CLI AOT compilation and development tooling.

### 3.2 TypeScript Runtime & Core (`packages/core`, `packages/runtime`, `packages/compiler-runtime`)
- **Status**: Class decorator `@Component` binds metadata (`selector`, `templateUrl`, `styleUrl`). Hierarchical DI provides parent-fallback injectors and circular dependency diagnostics.
- **Identified Gaps**:
  - Missing first-class signal input/output primitives (`input<T>()`, `input.required<T>()`, `output<T>()`) in `@jarvis/core` matching modern signal ergonomics.
  - Runtime `compileComponent()` currently compiles templates dynamically at bootstrap if not pre-compiled; AOT workflow via CLI should generate statically resolved templates.

### 3.3 Reactive Engine (`packages/reactive`)
- **Status**: Implements push-pull reactive dependency graph with dynamic dependency cleanup, lazy memoized derivations (`computed`), microtask batching (`scheduleJob`, `batch`), and async `resource()`.
- **Status**: Zero RxJS dependencies. 100% verified with automated tests and micro-benchmarks (11M+ signal ops/sec).

### 3.4 Renderer Abstraction (`packages/renderer`)
- **Status**: Contains `Renderer` interface, `DOMRenderer`, `TestRenderer`, and optimal $O(N)$ `reconcileKeyedList`. Reconciles dynamic list items without creating or destroying unnecessary DOM nodes.

### 3.5 Routing System (`packages/router`)
- **Status**: Signal-based route parameters, query parameters, data inheritance, lazy-loading (`loadComponent`), parallel resolvers, route guards (`canMatch`, `canActivate`, `canDeactivate`), and named `<router-outlet>`.

### 3.6 CLI & Code Generation (`cli/`)
- **Status**: Basic `cli/src/index.ts` existed with minimal `component` and `service` scaffolding.
- **Identified Gaps**:
  - Lacked dedicated template assets directory (`cli/templates/`).
  - Lacked commands for `page`, `directive`, `pipe`, `guard`, `model`, and `repository`.
  - Did not generate standard colocated `.spec.ts` test files for all entity types.
  - Did not scaffold complete feature-based application trees (`jarvis create app <name>`).

## 4. Architectural Separation: Framework vs. Generated Applications

A critical requirement of this architecture is maintaining strict separation between:

### A. The JARVIS Framework Repository
- Package-based monorepo housing compiler crates, runtime libraries, rendering engines, and developer tools.
- Strict package dependency hierarchy (leaf packages: `reactive`, `renderer`; consumer packages: `core`, `router`, `runtime`).

### B. Generated JARVIS Applications
- Feature-based project layout generated by the CLI.
- No framework source files inside application directories.
- Clean separation between business features (`src/features/*`), shared reusable components (`src/shared/*`), and core singleton infrastructure (`src/core/*`).

## 5. Proposed Changes & Action Plan

1. **Core Signal Input/Output APIs**:
   - Implement `input<T>()`, `input.required<T>()`, and `output<T>()` in `packages/core/src/input_output.ts`.
   - Re-export them from `packages/core/src/index.ts`.

2. **CLI Scaffolding Expansion**:
   - Implement complete generators in `cli/src/generator.ts`:
     - `create app <name>`: Full Angular-inspired, feature-based application with `src/app/`, `src/features/`, `src/shared/`, `src/core/`, `src/styles/`, `jarvis.config.ts`, `package.json`, and `tsconfig.json`.
     - `generate component <name>`: `.component.ts`, `.component.html`, `.component.css`, `.component.spec.ts`.
     - `generate page <name>`: `.page.ts`, `.page.html`, `.page.css`, `.page.spec.ts`.
     - `generate service <name>`: `.service.ts`, `.service.spec.ts`.
     - `generate directive <name>`: `.directive.ts`, `.directive.spec.ts`.
     - `generate pipe <name>`: `.pipe.ts`, `.pipe.spec.ts`.
     - `generate guard <name>`: `.guard.ts`, `.guard.spec.ts`.
     - `generate model <name>`: `.model.ts`.
     - `generate repository <name>`: `.repository.ts`, `-repository.interface.ts`.
   - Add template assets in `cli/templates/`.

3. **Complete Documentation Suite**:
   - Deliver 10 comprehensive architectural specifications in `docs/architecture/`.

4. **Automated Verification**:
   - Run unit and integration tests verifying code generation, component instantiation, and compiler compatibility.
